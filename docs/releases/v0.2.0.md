# Release Notes — v0.2.0

`basis-console` `v0.2.0` brings **operation-aware authorization** into the
Decision Simulator through `basis-gateway`, while preserving the legacy
evaluation workflow unchanged. This is a release-preparation and
release-readiness pass over already-implemented, already-tested code (see
`docs/architecture.md`, Phases 16–20); it introduces no new product behavior
beyond what those phases delivered.

> **Release readiness is not production readiness.** A `v0.2.0` release means
> the console's interaction patterns, architectural boundaries, documentation,
> and quality gates are coherent and stable enough for early adopters to
> evaluate and build against. It does **not** mean the console has been
> audited or hardened for deployment in live operational technology
> environments. No production-readiness claims are made anywhere in this
> repository.

## Overview

The Decision Simulator now offers two explicit, independently selectable
evaluation contracts:

- **Legacy** (`evaluation_type=legacy`, the default and unchanged) —
  `POST /v1/evaluate`, as shipped in `v0.1.0`/`v0.1.1`.
- **Operation-aware** (`evaluation_type=operation_aware`, new) —
  `POST /v1/evaluate/operation-aware`. Submits only action / resource type /
  resource ID (no subject, no context — the endpoint has no field for
  either) and relays the kernel's governed result verbatim.

Both contracts support **preview mode** (build and display the exact request
shape without ever calling the gateway) and **live gateway submission** (when
a gateway base URL and server-side bearer token are configured). Operator and
Training presentation modes share the identical operation-aware workflow;
Training mode adds an educational panel only, never a behavior change.

## Highlights

- **Operation-aware Decision Simulator** — a second, explicit evaluation
  contract alongside the legacy one, selected per request.
- **Preview and live gateway modes** — independent of which contract is
  selected; preview never contacts the gateway.
- **Semantic outcome/disposition/status separation** — evaluation status,
  kernel outcome (`allow` / `deny` / `not_applicable`), governed failure
  reason, gateway disposition, HTTP status, and console client status are
  kept visually and textually distinct, never collapsed into one another.
- **Evidence provenance** — every displayed fact is labelled as submitted
  input, returned evidence, console explanation, or future capability.
- **Operator/Training parity** — both presentation modes render the identical
  shared result; Training mode adds one additional educational section.
- **Training-mode education** — an ecosystem-flow diagram, provenance legend,
  and vocabulary glossary alongside the shared result.
- **Security and diagnostic hardening** — strict typed response parsing,
  correlation-ID integrity checking, redacted diagnostics, HTML-escaping of
  gateway-returned and submitted values, and server-side rejection of
  crafted legacy-only fields in operation-aware mode. See the "Security
  posture" section below and the `CHANGELOG.md` `### Security` entry for
  `v0.2.0`.

## Existing legacy capability

- The legacy Decision Simulator remains available and **is the default**
  (`evaluation_type=legacy`).
- Legacy preview (request-shape validation without a gateway call) remains
  supported.
- Legacy `POST /v1/evaluate` live submission remains supported, unchanged.

## Compatibility

- **Python:** `>=3.10` (unchanged from `v0.1.0`).
- **Runtime dependencies:** `fastapi>=0.111.0`, `uvicorn[standard]>=0.29.0`,
  `jinja2>=3.1.0`, `pydantic>=2.7.0`, `pydantic-settings>=2.3.0`,
  `httpx>=0.27.0` — bounds unchanged for this release; no dependency was added
  or upgraded to deliver operation-aware support (see "Dependency review"
  below).
- **Gateway compatibility:** live operation-aware evaluation requires a
  `basis-gateway` instance exposing `POST /v1/evaluate/operation-aware`
  (`OPERATION_AWARE_ENABLED` on the gateway). Legacy evaluation continues to
  require only `POST /v1/evaluate`, as before. If the gateway does not expose
  the operation-aware endpoint, the console reports `capability_unavailable`
  honestly rather than erroring or fabricating a result.
- **Environment variables:** no new environment variable was introduced for
  this release. `GATEWAY_BASE_URL` and `GATEWAY_BEARER_TOKEN` govern both the
  legacy and operation-aware contracts identically; `BASIS_CONSOLE_MODE`
  continues to select `operator` (default) or `training`.
- **Legacy-path compatibility:** no request field, response contract, or
  evaluation behavior changed for existing legacy usage.
- **Migration:** none required. Deployments that only use the legacy contract
  are unaffected by upgrading.

## Upgrade guidance

```bash
git pull
python -m pip install -e '.[dev]'   # or: make install
```

No new environment variables are required to adopt `v0.2.0`. To exercise the
operation-aware contract against a live gateway, point the existing
`GATEWAY_BASE_URL` / `GATEWAY_BEARER_TOKEN` variables at a `basis-gateway`
instance with `OPERATION_AWARE_ENABLED` set — the same variables already used
for legacy live evaluation.

## Known limitations

This release does not provide:

- local policy evaluation;
- policy loading or editing in the console;
- arbitrary operation-aware caller context;
- caller-asserted subject identity;
- caller-asserted producer evidence;
- authenticated-subject details in the operation-aware response;
- live producer-trust details in the operation-aware response;
- embedded evaluation traces;
- trace retrieval or visualization;
- audit-event retrieval or viewing;
- identity telemetry;
- southbound OT execution;
- deployment automation;
- production certification.

## Security posture

- The console delegates authorization to `basis-gateway`; it does not
  evaluate policy locally.
- The console does not decode bearer tokens to infer a subject — live
  evaluation derives the subject entirely from the gateway's verification of
  the token.
- Operation-aware caller context is restricted: there is no control for
  arbitrary context, subject ID, or subject type, and a crafted non-empty
  value is rejected server-side regardless of what the browser renders or
  disables.
- Diagnostics (generic/client failures, contract-invalid responses) are
  redacted before display; credential-shaped fields never render, even in
  diagnostic output.
- Rendered untrusted values (gateway-returned reason codes, explanations,
  error text, and submitted input) remain autoescaped; no template in this
  codebase uses `|safe`.

This is a security-conscious hardening pass, not a formal security
certification or third-party audit. See `SECURITY.md` for the console's full
security model and how to report a vulnerability.

## Future phases

Beyond `v0.2.0`, expected directions (each owned at the appropriate boundary,
not invented by the console): live gateway-backed policy/audit-history/
resource-catalog views once the gateway exposes console-facing endpoints; a
future `basis-schemas` package replacing `basis_console.vocabulary`; a future
`basis-identity` service the console will display but never implement;
evaluation-trace retrieval and visualization; an audit-event viewer; and
deployment packaging. None of these are included in this release.

See [`docs/architecture.md`](../architecture.md) for the full boundary set and
phase-by-phase notes, and [`docs/releases/v0.1.0.md`](v0.1.0.md) for the prior
release.
